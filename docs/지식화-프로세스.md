# 지식화 프로세스 — 재사용 모듈

> **모듈 문서:** 다른 프로젝트에서도 가져다 쓰는 작업 방식이다. 착한가격 지도가 첫 적용 사례이고, 근거는 [사례지식](사례지식.md) 장 번호와 [지식화기록](지식화기록.md)으로 연결한다.
> 대상: 긴 작업을 하면서 **세부가 사라지기 전에 지식으로 남기고**, 여러 문서가 서로 어긋나지 않게 유지하는 방법.
> 안정화 후 스킬(절차)·기본 지침(공통 원칙)으로 올릴 1차 재료. 갱신 규칙은 8장.

---

## 1. 왜 필요한가

- 긴 대화는 요약되면서 세부(수치·판단 근거)가 사라진다. 실제로 착한가격 지도 정리 때 요약본만으로는 부족해 **전체 대화 기록을 다시 읽어야** 했다.
- 목표는 서비스 하나가 아니라 **다음 프로젝트에서 같은 조사·실수를 반복하지 않는 것**.

---

## 2. 세 겹 구조

| 층 | 언제 | 무엇을 | 방법 |
|---|---|---|---|
| ① 작업 중 즉시 기록 | 버그 수정·설정 변경·결정 직후 | 버그이력(원인·재발 방지), 배포설정기록, 운영절차, 배포전검토, 해당 모듈 | Claude 메모 규칙("고칠 때마다 버그이력 갱신, 원칙이 바뀌면 모듈도")으로 매 작업에 자동 적용 |
| ② 정기 점검 | 안정화 기간 매주 → 이후 **실제 운영 주기**(예: 공공데이터 분기 갱신 직후) | 새 교훈 반영, 시간이 지나면 바뀌는 정보(한도·플랫폼) 최신화, **문서 정합성 점검**, 스킬·지침화 후보 | Claude 데스크톱 **예약 작업**(로컬 실행) |
| ③ 공개 | 사용자 승인 후 | GitHub 업로드 | 예약 작업은 문서만 고치고 알림 → "올려" 승인 시 커밋·push |

## 3. 문서 구조 — 사례 문서 + 모듈 + 사건 기록

| 종류 | 담는 것 | 예(착한가격 지도) |
|---|---|---|
| **사례 문서** | 이 프로젝트에서 왜 그렇게 했나 — 원칙과 근거, 모듈로 가는 요약·링크 | [사례지식](사례지식.md) |
| **모듈 문서** | 다른 업무에서도 계속 쓰는 주제별 설계 — 원칙 + 근거 번호 + 적용 순서 + 변경 이력 + 갱신 규칙 | [분류·검색 매핑](분류-검색매핑.md), [공공데이터 파이프라인](공공데이터-파이프라인.md), [외부 플랫폼 레퍼런스](외부플랫폼-레퍼런스.md), 이 문서 |
| **사건 기록** | 무엇이 틀렸고 어떻게 막나(번호) + 회귀 확인 문장 | [버그이력](버그이력.md) |
| **절차 기록** | 어디서 무엇을 설정했나, 운영 순서 | [배포설정기록](배포설정기록.md), [운영절차](운영절차.md) |
| **점검 이력** | 언제 무엇을 반영했나, 기준 커밋 | [지식화기록](지식화기록.md) |

**모듈로 떼는 기준:** 한 주제가 계속 커지고(버그·원칙이 계속 붙음) 다른 업무에서도 쓰일 때, 또는 시간이 지나면 바뀌는 정보라 한 곳에서 갱신해야 할 때.

**역할 분담(중복 금지):** 사건은 사건 기록에만, 원칙과 근거 번호는 모듈에만, 사례 문서는 요약과 링크만. 같은 내용이 두 곳에서 따로 바뀌지 않게 한다. 사례 문서에서 옮긴 장은 **제목(장 번호)을 그대로 두고** 본문만 요약+링크로 바꾼다 → 다른 문서의 "사례지식 3-8" 같은 참조가 깨지지 않는다.

## 4. 문서 연동 — 한 곳이 바뀌면 어디를 같이 고치나

| 바뀐 것 | 같이 고칠 곳 |
|---|---|
| 새 버그 (버그이력) | 요약 표 행 + 상세 절 둘 다 / 해당 모듈의 원칙·변경 이력(새 원칙일 때) / 회귀 문장 |
| 모듈의 원칙·장 번호 | 사례 문서의 요약 줄, 다른 모듈의 링크 |
| 새 모듈 | 사례 문서 머리말·문서 지도, README 문서 목록, 예약 작업 점검 대상은 **자동**(모듈 표시로 인식) |
| 코드 이름·파일 이름 | 모듈의 코드 위치 표 |
| 외부 플랫폼 조건 | 외부 플랫폼 레퍼런스(확인 날짜 포함), 설정 절차면 배포설정기록 |

**자동 정합성 점검 — `check_docs.py`**

문서를 고친 뒤와 정기 점검 때 실행한다. FAIL이 있으면 고친 뒤 올린다.

| 점검 | 잡는 것 |
|---|---|
| 링크 | 없는 파일, 공개 저장소에 없는 파일(추적 안 됨)을 가리키는 링크 |
| 버그 번호 | 요약 표와 상세 절이 서로 빠짐 없는지(#51 요약 행 누락 같은 것), 문서에 적힌 #번호가 실제로 있는지 |
| 모듈 형식 | 모듈 표시가 있는 문서마다 변경 이력·갱신 규칙 절, 사례지식으로 가는 링크, 사례지식·README에서 오는 링크 |
| 장 참조 | 모듈에 적힌 "사례지식 N-N"이 실제 장 제목으로 있는지 |
| 코드 참조 | 모듈에 적힌 코드 이름·파일 이름이 실제 코드에 있는지(코드가 바뀌면 문서가 낡았다는 신호) |
| 흡수 확인(경고) | 분류별 버그가 담당 모듈에 인용됐는지(예: `해석` 버그 → 분류·검색 매핑) — 새 버그가 모듈에 반영 안 됐다는 신호 |
| 신선도(경고) | 외부 플랫폼 레퍼런스의 "마지막 확인"이 120일 넘음 |

모듈 인식: 문서 맨 위에 `> **모듈 문서:**` 표시가 있으면 모듈로 본다. 새 모듈을 만들면 점검 대상에 자동으로 들어간다.

## 5. 설계 판단

- **시간 + 사건 혼합:** 지식은 작업해야 생긴다. 시간 기반만 쓰면 헛돌고, 사건 기반만 쓰면 빠뜨린다 → 작업 중 기록(사건) + 정기 점검(시간)으로 보완.
- **단기 촘촘 → 장기 느슨:** 안정화 기간엔 변화가 많아 주간, 이후엔 실제 운영 주기(분기 데이터 갱신)에 맞춤.
- **기준 커밋으로 이어서 점검:** 지식화기록 마지막 행의 기준 커밋·점검일 **이후 변경만** 검토 → 중복 정리 방지, 변경 없으면 알림 없이 종료. 작업 중 수동으로 정리했으면 그때도 행을 추가해 다음 점검이 중복하지 않게 한다.
- **사람 판단은 사람에게, 기계 점검은 스크립트에게:** 링크·번호·코드 이름처럼 규칙으로 판정되는 것은 `check_docs.py`, 무엇이 새 원칙인지는 점검 작업(Claude)이 판단하고 사용자가 승인.
- **예약 작업 종류 선택:** 대화창 안 예약은 창을 닫으면 사라지고, 클라우드 예약은 PC의 문서·대화 기록에 접근 불가 → **로컬 예약 작업**.
- **자기 관리:** 주간 작업은 기간이 끝나면 스스로 끄고, 분기 작업은 매번 다음 분기로 **스스로 재예약**.
- **공개 저장소 안전장치:** 자동 커밋·push 금지, 키·계정·개인 이름 금지, 앱 코드는 수정 금지(문서만).
- **첫 실행은 직접 시험:** 예약 작업은 첫 도구 사용에서 권한 승인을 기다리며 멈춘다. "지금 실행"으로 한 번 돌려 승인해 두면 이후 자동 실행이 멈추지 않는다.
- **제약:** 앱이 꺼져 있으면 다음 실행 시 수행.

## 6. 전체 대화에서 지식 뽑는 방법

1. 대화 기록(jsonl)에서 **사용자 메시지**와 **Claude 답변의 본문 텍스트**만 추출(도구 결과·첨부 스킬 원문 제외).
2. 사용자 메시지 흐름을 먼저 읽어 **결정·통찰·피드백 지점**을 잡는다.
3. 요약에서 압축된 구간(착한가격 지도에서는 첫날 데이터 작업)은 Claude 답변을 **시간 구간별로 잘라** 수치·근거를 복원.
4. 관점별(데이터·설계·디자인·UX·배포·기능·협업)로 "원칙 → 근거" 정리, 세부는 전용 문서로 링크.
5. 공개 전 개인 정보 검사(이름·계정·키) 후 업로드.

## 7. 다른 프로젝트에 적용하는 순서

- [ ] 첫날에 `docs/`와 문서 지도(사례 문서·사건 기록·절차 기록·점검 이력)를 만들고, 메모에 "고칠 때마다 기록" 규칙을 둔다
- [ ] 이 프로젝트의 `check_docs.py`를 복사해 문서 이름·분류별 담당 모듈만 바꿔 쓴다
- [ ] 주제가 커지면 모듈로 떼고(3장 기준), 옮긴 장은 제목을 남기고 요약+링크
- [ ] 배포 후 예약 작업(주간 → 운영 주기)과 지식화기록 기준점을 만들고, 예약 작업에 `check_docs.py` 실행을 넣는다
- [ ] 예약 작업은 "지금 실행"으로 한 번 시험해 권한을 승인해 둔다
- [ ] 공개 저장소면 예약 작업의 커밋·push는 승인 후로
- [ ] 안정화 후 사례 문서·모듈 → 스킬(절차) / 기본 지침(공통 원칙)으로 승격

**착한가격 지도 적용 예시:** 예약 작업 `goodprice-knowledge-weekly`(2026-09-28~10-19 매주 월 10시, 기간 후 스스로 종료), `goodprice-knowledge-quarterly`(2026-11-02 10시 첫 실행, 공공데이터 갱신 후 첫 월요일로 스스로 재예약). 점검 이력은 [지식화기록](지식화기록.md).

---

## 8. 갱신 규칙

- 지식화 방식(주기·역할 분담·점검 항목)을 바꾸면 이 문서와 예약 작업 지시문을 함께 고친다.
- `check_docs.py`에 점검을 추가하면 4장 표에 한 줄 추가한다.
- 정기 점검에서 반복해서 걸리는 문제는 점검 규칙으로 만든다(사람이 매번 보지 않게).
