# 공공데이터 결합·매칭·검증 파이프라인 — 재사용 모듈

> **모듈 문서:** 다른 프로젝트에서도 가져다 쓰는 설계를 모은 문서다. 착한가격 지도가 첫 적용 사례이고, 근거는 [사례지식](사례지식.md) 장 번호와 [버그이력](버그이력.md) 번호(#)로 연결한다.
> 대상 상황: 공공데이터(주소·업소명·연락처 중심, 좌표·고유ID 없음)를 **지도·플랫폼 장소와 연결**하고, 실재 여부를 확인하며, **분기마다 갱신**해야 할 때.
> 실행 명령과 순서는 [운영절차](운영절차.md), 외부 API 조건과 한도는 [외부 플랫폼 레퍼런스](외부플랫폼-레퍼런스.md). 갱신 규칙은 9장.

---

## 0. 한눈에

```
[수집]  공공데이터 원본 + 같은 기관 서비스 화면 뒤 데이터(좌표·ID·사진·영업시간) + 상가정보 전국 파일
[결합]  출처 간 대조(업소명+주소 → 유사도) → 기준일 차이로 신규·취소 해석
[ID]    번호 대장으로 영구 ID 부여(새 업소만 새 번호)
[주소]  표기 정리 → 도로명주소 대조 → 건물관리번호·층(비교·식별용), 원문은 표시용으로 보존
[분류]  지난 분기와 번호별 비교 → 기존·추가·제외, 기존 업소의 항목별 변경 → 변경 보고서 → 사람 확인
[좌표]  오류 찾기 → 주소검색 → 장소검색 → 공공 좌표, 출처·신뢰도·확인일 기록
[매칭]  플랫폼 장소 ID(점수화 + 거리로 등급 재분할)
[검증]  싼 채널부터 교차검증: 카카오 → 네이버 → 전화 → 행정·세무 → 남은 것만 사람
[검사]  불변조건 자동 검사(check_data.py) → 실패하면 배포 중단
[갱신]  분기마다 이전과 비교해 바뀐 것만 처리
```

착한가격 지도 실적: 12,645건 원본 → 13,117곳, 좌표 100%, 검수 대상 2,615 → **245건(1.9%)**. 근거: [사례지식](사례지식.md) 1장.

## 2. 출처 조사

- **공식 오픈데이터보다 같은 기관 서비스 화면 뒤 데이터가 더 풍부할 수 있다.** 오픈데이터 스펙만 보고 설계하지 말고, 같은 기관의 서비스 화면이 무엇을 쓰는지 먼저 본다. 단 robots.txt·부담·권리(후기·사진)를 함께 확인. 근거: 공공데이터포털 CSV에는 좌표·ID·영업시간·사진이 없었지만 공식 누리집에는 모두 있었고, 시도별 16회 요청으로 12,882건 좌표 확보 → [사례지식](사례지식.md) 1-1.
- **두 출처의 차집합은 "오류"가 아니라 시간 차(신규·취소)를 드러낸다.** 기준일을 항상 같이 본다. 근거: CSV에만 218건(지정 취소 가능성), 사이트에만 473건(신규 지정) → [사례지식](사례지식.md) 1-2.
- **더 최신인 출처를 우선한다.** 정기 파일(CSV)은 시점 고정, 서비스 화면(사이트)은 현재 상태. 합집합으로 보여 주면 **같은 가게가 두 번**(표기 차이·상호 변경) 나오고 지정 해제된 곳도 남는다 → 옛 출처에만 있는 것은 숨김 후보로 분류하고, 같은 가게면 대체 번호로 잇는다(#54).
- **출처별 정보 범위가 다르다:** CSV(목록·메뉴 4개), 사이트 엑셀(편의시설 14종·대표 메뉴 1개), 사이트 지도(좌표·공식 업소번호·세부업종), 사이트 상세(영업시간·전체 메뉴·사진·담당 부서). 영업시간은 상세에만 있어 분기마다 전체 재수집이 필요하다.

## 3. 원천 데이터 오류 유형 (다른 공공데이터에도 흔함)

- 일괄 치환 사고: "서광주로" → "서**광주광역시**로" (시도명 치환이 도로명까지 바꿈).
- 오타·번지 오류: 양지면 76-4 → 실제 양지**읍** 73-4.
- 주소 뒤에 업소명·상가명 붙음, 지번을 도로명처럼 기재.
- 행정구역 개편 미반영: 인천 동구 → 제물포구, 광주+전남 → 전남광주통합특별시.
- 시군구 칸에 도로명(세종 등, #18), 영업시간 해석 실패(자정 넘김 21곳, #24), 가격 이상치(0원·1원, PT 66만 원 회차권).
- 도로명주소 전수 점검 결과: 원문 정상 93.8%, 정제 후 정상 4.4%, **존재하지 않는 주소 1.8%(241건)**.
- **칸 이름만 보고 내용을 짐작하지 말 것.** '개방시간'이 시각이 아니라 코드(상시·정시·불규칙·미개방)였고 시각은 상세 칸에 자유 형식으로 있었다 → 자유입력 칸은 **값 목록부터** 뽑아 유형을 나눈다(화장실 찾기 사례).
- **코드 칸과 자유입력 칸이 어긋나면, 정보가 더 많은 쪽을 쓰고 출처를 밝힌다.** 코드가 '불규칙'인데 상세에 `08:00~24:00`이 적혀 있으면 담당자가 코드를 잘못 고른 것이다 — 시각으로 계산하되 화면에 "적힌 시각 기준(원본 표기 '불규칙')"을 적어 **어느 칸을 믿었는지** 사용자가 알게 한다. 코드를 그대로 따르면 한 지역(대구 중구 78%)이 통째로 "확인 필요"가 되어 서비스가 비어 보인다(화장실 6-4).
- **캐시와 기준본은 자산이다.** 주소·지도 API 캐시를 잃으면 수십만 회를 다시 부르고, 번호 대장을 잃으면 공유 링크가 무효가 된다 → 비공개 백업 + 기준본 보관 정책(최근 8주 전체 → 월 1개 → 연 1개).
- **골든 표본으로 규칙 변경을 지킨다.** 대표 100곳의 결과(좌표·등급·상태)를 고정해 두고 규칙을 고칠 때마다 비교하면, 한 곳을 고치다 다른 곳이 망가지는 것을 바로 본다.
- **원칙:** 공공데이터는 "관리 책임이 지자체에 있는 원본"이다. 우리는 보정·표시만 하고, 원천 수정은 **공식 오류 신고 창구**로 돌린다.

## 4. 매칭 — 공통 키가 없을 때

1. **거리 + 이름 유사도 + 전화번호**로 점수화, 신뢰도 등급(HIGH/MID/LOW/미매칭).
2. 등급을 **거리로 다시 쪼개면** 판단이 선명해진다: LOW 562건 중 30m 이내 459건(82%)은 같은 가게(간판·상호 표기 차이), 100m 초과 65건은 엉뚱한 가게.
3. 유사도 계산의 한계를 알아둔다: `ROCOCO` ↔ `로코코`는 유사도 0.00(영·한 표기).
4. **같은 장소 ID에 두 업소**가 붙으면 한쪽은 틀림(장소 ID는 건물이 아니라 가게 단위) → 이름이 더 비슷한 쪽이 갖고 나머지는 재검증.
5. 교차검증 채널을 **싼 것부터** 순서대로: 카카오 → 네이버 → 전화 → 행정·세무. 검수 대상 2,615 → 948 → 659 → **245**.

**사업장명과 간판명은 다르다 (사용자 통찰)**
- 사업자등록 상호 ≠ 실제 간판. `까꼬뽀꼬미용실` ↔ `까꼬뽀꼬헤어샵`, `송이향(칼국수전문점)` ↔ `송이향`.
- → LOW라도 근거리면 자동 채택, 전화번호가 같으면 이름·거리와 무관하게 같은 업소.

**좌표 하나의 역할을 과대평가하지 않기**
- 좌표(WGS84)는 어느 지도든 **같은 위치에 핀**을 찍게 해 준다.
- 그러나 가게 페이지로 연결하려면 **플랫폼별 장소 ID**가 필요하다. 좌표는 그 ID를 찾는 검색 범위(반경 50~300m)를 좁히는 **기준점**.

**플랫폼 등록률은 업종마다 다르다** — 단일 플랫폼 매칭률로 품질을 판단하지 말 것. 근거: 카카오 매칭률 중식 84.0% ↔ 세탁 62.7%, 카카오에 없던 2,258건 중 1,528건이 네이버에 있었다 → [사례지식](사례지식.md) 1-3.

## 5. ID 설계 — 외부 ID와 영구 ID

| ID | 성격 | 설계 |
|---|---|---|
| 우리 관리번호(GP#####) | **영구**, 외부 노출(공유 링크·저장) | 번호 대장으로 고정, 재사용 금지 |
| 카카오 장소 ID | 이전하면 새 ID가 되는 경우가 많음 | 확인일과 함께 저장, 분기마다 재확인 |
| 구글 place_id | 유지되기도 하지만 바뀔 수 있음 | (이번엔 미사용) 12개월 넘으면 재확인 |
| 공식 사이트 업소번호 | 지자체 기록 기준 | 같은 업소 판별의 1순위 키 |
- 순번 ID를 외부에 노출했다가 **분기 업데이트마다 번호가 밀리는 치명 오류**가 날 뻔했다(#29).

**번호 대장(영구 ID) 설계**
- 같은 업소 판별 키: 공식 업소번호 → 시도+업소명+주소 → (업소번호 없는 곳) **건물관리번호+업소명** — 주소 글자가 조금 달라져도 같은 건물·같은 이름이면 같은 번호.
- 줄 순서가 아니라 키로 찾으므로 원본의 **순서가 밀려도 번호는 그대로**(#29).
- 한 번 준 번호는 영구, 새 업소만 새 번호, 삭제 번호 재사용 금지, 제외는 별도 목록(`data/exclude_ids.json`).
- 모의 테스트(1곳 삭제+1곳 추가+순서 섞기)로 13,117곳 번호 유지 확인.

## 6. 좌표 보정 절차

1. **오류 찾기(자동):** 좌표 없음 / 시군구 경계 밖 / 주소를 다시 변환한 좌표와 **200m 이상** 차이 / 여러 업소가 같은 좌표(관청 좌표를 기본값으로 넣은 의심) / 좌표 주변에 해당 상호 없음.
2. **고치기(자동 → 수동):** 주소 정리(괄호·층·호 제거) → 카카오 **주소검색** → 카카오 **장소검색**(업소명+시군구) → 공공 좌표(도로명주소·브이월드). 결과가 서로 가까우면 채택, 엇갈리면 검수.
3. **기록:** 업소마다 **좌표 출처 · 신뢰도 · 확인일**. 수기 보정은 **별도 보정 파일**에 저장해 다음 분기에 덮어써지지 않게.
4. 끝까지 못 정하면 지도에는 숨기고 목록에 "위치 확인 중".
- 이번 결과: 좌표 없던 236건 → 주소검색 231 + 장소검색 5 = **100% 확보**, 실패 3건은 모두 원천 오타였다.

## 7. 검증·품질

**영세 업소의 "온라인 부재"는 행정·세무 데이터로 잡는다** — "검색에 안 나온다 = 폐업"은 고령·영세 업소에서 틀린다. 실재 확인의 최종 근거는 **행정·세무·카드 매출** 계열 데이터. 근거: 카카오 10,503 → 네이버 +1,667 → 전화번호 +289 → 소상공인 상가정보 +414 → 남은 245건 → [사례지식](사례지식.md) 1-4.

**품질 지표는 여러 개로 나눠 본다**
- 최종: 좌표 100%, 카카오 장소 ID 80.0%, 공식 사진 94.8%, 확정 등급(카카오+전화) 82.3%, 네이버 확정 12.7%, 상가정보 확정 3.2%, 검수 1.9%, 주소 정상 98.2%.
- 하나의 "정확도" 숫자보다 **무엇이 어떤 근거로 확정됐는지**를 등급으로 남기는 게 운영·설명에 유리.

**검증은 두 경로로**
- 엑셀 산출물은 **Excel 재계산 수식 오류 0건 + Python 독립 계산 대조**("김밥" 검색 414건 일치, 시도×업종 합계 13,118 일치).
- 앱 데이터는 `check_data.py`로 **불변조건 자동 검사**(ID 유지, 오픈=마감 0건, 시군구 형식, 좌표 범위, 증감, 알 수 없는 업종·세부분류) — 일부러 넣은 오류 3건 검출 확인. 검사 규칙은 버그이력에서 나온 것(#18, #23, #24, #29, #51).

**검수 운영 설계 — 사람이 볼 것만 남기기**

| 단계 | 담당 | 내용 |
|---|---|---|
| ① 자동 보정 | 스크립트 | API로 다시 찾고, 결과가 일치하면 자동 확정 |
| ② 1차 판단 | Claude | 남은 건마다 근거(거리·유사도·검색 결과·지도 링크)를 붙여 승인/수정/보류 추천 |
| ③ 최종 결정 | 사용자 | 보류·추천 건만 훑어보고 승인·수정·제외 |
| ④ 반영 | 스크립트 | 결정을 보정 파일에 저장, 다음 분기에도 유지 |
- **엑셀 검수 시트:** 한 줄에 판정 근거와 링크(공식·카카오·네이버·구글·로드뷰), 노란 칸에 결정·수정주소·참고링크·메모.
- **참고 링크 붙여넣기:** 검수자가 카카오·네이버·구글에서 직접 찾은 가게 링크를 붙이면 스크립트가 **장소 ID를 뽑아** 정확한 가게 링크로 교체(단축 링크는 풀어서). 자동 수집이 금지된 네이버도 **사람이 확인한 건은** 정확한 플레이스 링크가 된다.
- 원천 데이터 자체 오류(가격 1원·폐업·주소 오류)는 우리가 고칠 대상이 아니라 **공식 오류 신고 창구**로.
- 로드뷰는 검수 도구로도 유용(간판 확인). 단 촬영 시점이 1~3년 전일 수 있어 참고용.
- 노력 대비 실익 판단: 남은 245건은 포털·후기·사진이 모두 없어 **검수 중단**(사용자 결정).

## 8. 분기 갱신 설계

| 구분 | 판단 | 처리 |
|---|---|---|
| 유지 | 업소명·주소·내용 동일 | 기존 좌표·장소 ID 재사용(API 호출 없음) |
| 정보변경 | 업소명·주소 동일, 메뉴·가격·전화 변경 | 값만 갱신, **가격 이력 기록** |
| 이전 | 업소명·전화 동일, 주소 다름 | 좌표·매칭 다시 |
| 상호변경 의심 | 주소·전화 동일, 업소명 다름 | 검수 |
| 신규 | 대응 업소 없음 | 좌표·매칭 |
| 제외 | 새 데이터에서 사라짐 | 숨김(삭제 대신 이력 보관) |
**갱신 흐름(2026-09-22 구현):** 수집 → 고유번호 → 주소 정제 → 상세 **전체 다시 수집** → 상가정보 대사 → **변경 분류** → (사람 확인) → 필요한 곳만 매칭 → 검사 → 배포 → 다음 분기 비교 기준(스냅숏) 저장. 명령 순서는 [운영절차](운영절차.md) 1-2.

**변경 분류 규칙 (`diff_update.py`)**

| 분류 | 판단 | 처리 |
|---|---|---|
| 추가 | 지난 분기에 없던 번호 | 매칭·검증·상세·사진 축소본 |
| 제외 | 이번에 없는 번호 | 숨김, 번호 영구 보관 |
| 기존 · 변경 없음 | 항목 변화 없음. **같은 건물 안 층 이동·주소 표기 차이도 변경 없음**(표시 주소만 갱신) | 이전 결과 재사용 |
| 기존 · 세부정보 변경 | 가격·메뉴·영업시간·전화·편의시설·사진 중 변화 | 반영, 가격은 변경 기록(changes.csv) |
| 기존 · 업체명 변경 | 이름이 다름. 공식 업소번호가 같으면 **확정**, 아니면 **의심 → 확인 목록** | 카카오 재매칭·네이버 재검증 |
| 기존 · 이전 | **건물관리번호가 바뀜**(없으면 도로명+건물번호, 좌표 100m) | 재매칭·재검증 |
| 제외+신규 짝 | 제외 1곳과 추가 1곳이 같은 건물·같은 전화 | 확인 목록(추천: 번호 이어받기 → `--apply-review`) |
| **CSV에만 있음** | 공공데이터 CSV에만 있고 공식 사이트에 없음(사이트가 최신 → 사이트 우선) | 숨김. 사이트에만 있는 업소와 같은 전화·건물이면 **중복·상호 변경 → 대체 번호로 연결**, 아니면 플랫폼에서 찾아지면 **지정 해제 추정**, 못 찾으면 **폐업·영업종료 추정**(#54) |

- 한 업소가 여러 항목에 걸칠 수 있다. 보고서는 **기존·추가·제외 수(검산 포함)**, 기존 업소의 **항목별 업소 수**, 확인 목록(추천값이 기본 결정)을 보여 준다.
- **다시 수집·다시 매칭의 이유:** 예전에는 이미 받은 업소를 건너뛰어, 가격·영업시간이 바뀌어도, 이전해도 옛 정보·옛 카카오 장소가 남을 수 있었다(#53). 상세는 매 분기 전체를 다시 받아 비교하고, 매칭은 분류가 지정한 곳만 다시 한다.
- **오등록 검사:** 카카오 장소 ID 하나가 두 업소에 붙음, 좌표와 장소 거리 200m 초과 → 확인 목록.
- **2026-09-22 첫 실행 결과:** 도로명주소 대조 결과는 이전과 동일(정상 12,877 · 주소없음 241), **건물관리번호 12,877곳(98.2%)**. 상가정보(2026-06 기준, 우리 업소가 있는 건물의 상가 89,101곳) 대사 **10,903곳(83.1%)** — 강함(이름 유사도 0.7 이상) 10,637 · 약함(참고) 266. 약함 구간은 표본에서 맞는 것(g2모텔↔지투모텔)과 틀린 것(제일분식↔엄마분식)이 섞여 판단에 쓰지 않는다. 업종 대분류(음식점 I2·숙박 I1·개인서비스 S2)가 다르면 이름이 아주 비슷할 때만 연결.
- **가짜 다음 분기 시험(`test_diff_update.py`):** 업체명 변경·가격·영업시간·전화·편의시설·이전·층 이동·제외·추가·제외+신규 짝·카카오 중복 15항목 통과.
- **매칭 검사는 최종 결과로:** 중간 결과(`kakao_match.csv`)의 중복은 뒤 단계에서 정리되므로 오탐. 최종 결과 기준 지금 남은 것: 장소 ID 중복 3건(예: 다른 가게가 옆 가게 장소에 연결), 좌표와 200m 초과 87곳(이름 같음 57곳 — 공식 좌표 오차가 많음) → 리허설·다음 갱신 때 확인 목록으로 재매칭.
- **상가정보는 근거:** 기준일 차이(파일은 분기 말 기준·약 1개월 뒤 공개)와 사업자 상호 ≠ 간판 때문에 판정에 쓰지 않는다. 지난 분기에 연결됐는데 사라지면 '폐업 의심'으로 확인 목록에만 올린다.
- **원본 이상 감지 → 반영 중단:** 항목 구성 변경, 전체 건수 **10% 넘게 급감**, 빈 값 급증(`check_data.py`, `diff_update.py`).
- **새 분류 값**(업종·세부분류)이 생기면 검사가 멈추고, 화면 매핑은 [분류·검색 매핑](분류-검색매핑.md)에서 고친다(#51).
- 앱 데이터 주소에 기준일 버전을 붙여 사용자 브라우저가 새 데이터를 받게 한다(#32).
- **덤으로 생기는 기능:** 가격 이력이 쌓이면 "김밥 2,000원 → 2,500원(2026 4분기)" 같은 **가격 인상 표시**, 지역별 신규 지정·제외 추이(미구현 아이디어).
- 운영 선택지: 수동(분기 1회 PC 실행, 채택) / 자동(월 1회 공공데이터 수정일 확인 → 변경 보고서 → 승인 후 배포).
- **원본·중간 데이터는 공개 저장소에 없으므로 따로 백업한다.** 분기 갱신은 이전 매칭 결과를 재사용하므로, 잃으면 전체 재매칭이 필요하다 → 갱신 전후에 비공개 저장소로 백업(키 문자열이 들어간 파일이 있으면 백업 중단).

## 9. 다른 프로젝트에 적용하는 순서

- [ ] 공개 데이터 스펙 외에 **같은 기관 서비스의 데이터**를 먼저 조사(robots·부담·권리 확인)
- [ ] 결합 전 **기준일**을 맞추고, 차집합을 신규·취소로 해석
- [ ] 외부 노출 ID는 **처음부터 영구 ID**(번호 대장), 외부 ID는 확인일과 함께
- [ ] 좌표·매칭 결과에 **출처·신뢰도·확인일**, 수기 보정은 별도 파일로
- [ ] 매칭은 점수화 + **거리로 등급 재분할** + 싼 채널부터 교차검증
- [ ] 원천 오류는 보정·표시만, 원천 수정은 공식 창구로
- [ ] 사람 검수는 근거·링크를 붙인 목록으로, 남은 건은 노력 대비 실익으로 중단 판단
- [ ] 데이터 불변조건 자동 검사 → 실패 시 배포 중단, 검사 규칙은 버그마다 추가
- [ ] 분기 갱신은 이전 분기와 비교해 바뀐 것만, 이상 감지 시 반영 중단
- [ ] **"이미 한 곳은 건너뛰기" 캐시는 변경을 놓친다** — 비교 기준(스냅숏)을 남기고, 변경 분류 결과로 다시 할 곳을 정한다
- [ ] 주소는 글자가 아니라 **공식 건물 번호**로 비교한다(표기 차이·층 이동을 이전으로 오판하지 않게)

## 11. 갱신 규칙

- `데이터`·`운영` 분류 버그 중 파이프라인 관련 버그를 고치면: ① 버그이력에 사건 기록 ② 새 원칙이거나 검사 규칙이 늘었으면 이 문서의 해당 장과 10장을 고친다(근거는 버그 번호).
- 분기 데이터 갱신을 하면 실제 소요·신규·제외 건수와 막힌 단계를 8장 또는 10장에 남긴다.
- 스크립트 이름이 바뀌면 1장 표를 고친다(`check_docs.py`가 적힌 파일 이름을 확인한다).
