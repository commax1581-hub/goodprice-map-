## 0. 한 장 요약

| 구분 | 핵심 교훈 |
|---|---|
| 데이터 인사이트 | 공공데이터 원본은 **출발점일 뿐**. 같은 기관의 다른 창구(공식 누리집)에 더 풍부한 데이터가 있었다(좌표·사진·영업시간·전체 메뉴) |
| 데이터 리터러시 | "검색에 안 나옴 ≠ 폐업". 영세·고령 업소는 온라인에 없다 → **행정·세무 데이터**가 마지막 퍼즐 |
| 설계 | 공통 키가 없는 데이터 결합은 **점수 기반 매칭 + 단계적 교차검증**. 외부 ID는 믿는 값이 아니라 **다시 확인하는 값**, 내부 ID는 **영구** |
| 디자인 | 식별도는 공식 상징에서, 신뢰는 **출처·비공식 명시**에서. 색은 역할로 나눈다(파랑=신뢰, 노랑=가격) |
| UX | **탐색 순서와 카드 위계는 다르다.** 보여준 뒤 권하고(설치), 먼저 묻지 않는다 |
| 배포 | 무료 조합(GitHub + Cloudflare Pages + 카카오 + 제미나이 무료)으로 **운영비 0원**. 함정은 대부분 "콘솔 설정" |
| 기능 설정 | 규칙 우선 + AI 보조(하이브리드), 링크 연계(크롤링 대신), 실패 시 대체 경로를 항상 둔다 |

## 1. 데이터 인사이트 — 데이터에서 무엇을 발견했나

### 1-1. "공식 오픈데이터"보다 "공식 서비스 화면 뒤 데이터"가 더 풍부할 수 있다
- 공공데이터포털 CSV: 12,645건, 항목은 시도·업종·업소명·연락처·주소·메뉴1~4·가격. **좌표·고유ID·영업시간·사진 없음.**
- 같은 행안부의 공식 누리집(goodprice.go.kr): 카카오맵 기반이라 **업소별 좌표·고유번호·영업시간·편의시설 12종·사진·메뉴 무제한·지정메뉴 여부**가 있었다.
- 수집 부담 측정이 판단을 바꿨다: 예상 250회 → 실제 **시도별 16회 요청**(2초 간격)으로 12,882건 좌표 확보.
- **교훈:** 오픈데이터 스펙만 보고 설계하지 말고, 같은 기관의 서비스 화면이 무엇을 쓰는지 먼저 본다. 단 robots.txt·부담·권리(후기·사진)를 함께 확인.

### 1-2. 결합 결과 자체가 인사이트
| 결합 | 건수 | 읽을 거리 |
|---|---|---|
| 업소명+주소 완전 일치 | 11,859 | 같은 행정 시스템 출처라 대부분 그대로 맞음 |
| 업소명 일치+같은 시군구 | 342 | 지번↔도로명 표기 차이, 일부는 **실제 이전** 후보 |
| 주소 일치+업소명 유사 | 226 | 상호 표기 차이 |
| CSV에만 | 218 | 지정 취소 가능성 |
| 사이트에만 | 473 | CSV 기준일 이후 **신규 지정** |
- **교훈:** 두 출처의 차집합은 "오류"가 아니라 **시간 차(신규·취소)** 를 드러낸다. 기준일을 항상 같이 본다.

### 1-3. 플랫폼 등록률은 업종마다 다르다
- 카카오 장소 매칭률: 중식 84.0%, 양식 82.9%, 한식 82.7% ↔ **세탁 62.7%, 미용 64.8%, 목욕 66.1%, 이용 69.6%**.
- 카카오에 없던 2,258건 중 **1,528건이 네이버에는 있었다** → 동네 미용실·세탁소는 네이버 플레이스 쪽 등록이 많다.
- **교훈:** 단일 플랫폼 매칭률로 데이터 품질을 판단하지 말 것. 업종별로 보완 채널이 다르다.

### 1-4. 영세 업소의 "온라인 부재"를 잡은 것은 행정·세무 데이터
- 검수 단계별 확정: 카카오 10,503 → 네이버 +1,667 → 전화번호 +289 → **소상공인 상가정보(국세청·카드사) +414** → 남은 **245건(1.9%)**.
- 남은 245건도 82.4%는 공식 사이트에 지정 업소로 등록 → 폐업보다 **상호 변경·온라인 미등록** 가능성.
- 판단(사용자): 245건은 포털·후기·사진이 모두 없어 **노력 대비 실익 없음 → 중단**.
- **교훈:** "검색에 안 나온다 = 폐업"은 고령·영세 업소에서 틀린다. 실재 확인의 최종 근거는 **행정·세무·카드 매출** 계열 데이터.

### 1-5. 원천 데이터 오류 유형 (다른 공공데이터에도 흔함)
- 일괄 치환 사고: "서광주로" → "서**광주광역시**로" (시도명 치환이 도로명까지 바꿈).
- 오타·번지 오류: 양지면 76-4 → 실제 양지**읍** 73-4.
- 주소 뒤에 업소명·상가명 붙음, 지번을 도로명처럼 기재.
- 행정구역 개편 미반영: 인천 동구 → 제물포구, 광주+전남 → 전남광주통합특별시.
- 시군구 칸에 도로명(세종 등), 영업시간 해석 실패(자정 넘김 21곳), 가격 이상치(0원·1원, PT 66만 원 회차권).
- 도로명주소 전수 점검 결과: 원문 정상 93.8%, 정제 후 정상 4.4%, **존재하지 않는 주소 1.8%(241건)**.
- **교훈:** 공공데이터는 "관리 책임이 지자체에 있는 원본"이다. 우리는 보정·표시만 하고, 원천 수정은 **공식 오류 신고 창구**로 돌린다.

### 1-6. 데이터로 확인한 사용자 기준값
- 가격 분포(음식점): 3천 원 이하 16.0%, **5천 원 이하 30.8%**, 7천 원 이하 55.0%, 1만 원 이하 85.5%, 중간값 7,000원 → 가격 필터를 5천 원 고정 대신 **3천·5천·7천·1만 선택형**으로.
- 고유 메뉴명 8,056개, 상위 키워드 23개로 56.5%만 커버 → **품목 콤보박스 불가, 업종 칩 + 품목 검색**.
- 영업시간 보유 57.4%(해석 성공 97%) → "지금 영업 중"은 **등록 업소 기준**임을 표시.
- 사진 보유 94.8% → 목록 사진 중심 설계가 가능.

## 2. 데이터 리터러시 — 데이터를 어떻게 읽고 판단했나

### 2-1. 공통 키가 없을 때의 매칭 사고법
1. **거리 + 이름 유사도 + 전화번호**로 점수화, 신뢰도 등급(HIGH/MID/LOW/미매칭).
2. 등급을 **거리로 다시 쪼개면** 판단이 선명해진다: LOW 562건 중 30m 이내 459건(82%)은 같은 가게(간판·상호 표기 차이), 100m 초과 65건은 엉뚱한 가게.
3. 유사도 계산의 한계를 알아둔다: `ROCOCO` ↔ `로코코`는 유사도 0.00(영·한 표기).
4. **같은 장소 ID에 두 업소**가 붙으면 한쪽은 틀림(장소 ID는 건물이 아니라 가게 단위) → 이름이 더 비슷한 쪽이 갖고 나머지는 재검증.
5. 교차검증 채널을 **싼 것부터** 순서대로: 카카오 → 네이버 → 전화 → 행정·세무. 검수 대상 2,615 → 948 → 659 → **245**.

### 2-2. 사업장명과 간판명은 다르다 (사용자 통찰)
- 사업자등록 상호 ≠ 실제 간판. `까꼬뽀꼬미용실` ↔ `까꼬뽀꼬헤어샵`, `송이향(칼국수전문점)` ↔ `송이향`.
- → LOW라도 근거리면 자동 채택, 전화번호가 같으면 이름·거리와 무관하게 같은 업소.

### 2-3. 외부 ID의 성격을 구분한다
| ID | 성격 | 설계 |
|---|---|---|
| 우리 관리번호(GP#####) | **영구**, 외부 노출(공유 링크·저장) | 번호 대장으로 고정, 재사용 금지 |
| 카카오 장소 ID | 이전하면 새 ID가 되는 경우가 많음 | 확인일과 함께 저장, 분기마다 재확인 |
| 구글 place_id | 유지되기도 하지만 바뀔 수 있음 | (이번엔 미사용) 12개월 넘으면 재확인 |
| 공식 사이트 업소번호 | 지자체 기록 기준 | 같은 업소 판별의 1순위 키 |
- 순번 ID를 외부에 노출했다가 **분기 업데이트마다 번호가 밀리는 치명 오류**가 날 뻔했다(버그이력 #29).

### 2-4. 좌표 하나의 역할을 과대평가하지 않기
- 좌표(WGS84)는 어느 지도든 **같은 위치에 핀**을 찍게 해 준다.
- 그러나 가게 페이지로 연결하려면 **플랫폼별 장소 ID**가 필요하다. 좌표는 그 ID를 찾는 검색 범위(반경 50~300m)를 좁히는 **기준점**.

### 2-5. 품질 지표는 여러 개로 나눠 본다
- 최종: 좌표 100%, 카카오 장소 ID 80.0%, 공식 사진 94.8%, 확정 등급(카카오+전화) 82.3%, 네이버 확정 12.7%, 상가정보 확정 3.2%, 검수 1.9%, 주소 정상 98.2%.
- 하나의 "정확도" 숫자보다 **무엇이 어떤 근거로 확정됐는지**를 등급으로 남기는 게 운영·설명에 유리.

### 2-6. 검증은 두 경로로
- 엑셀 산출물은 **Excel 재계산 수식 오류 0건 + Python 독립 계산 대조**("김밥" 검색 414건 일치, 시도×업종 합계 13,118 일치).
- 앱 데이터는 `check_data.py`로 **불변조건 자동 검사**(ID 유지, 오픈=마감 0건, 시군구 형식, 좌표 범위, 증감) — 일부러 넣은 오류 3건 검출 확인.

## 3. 설계 — 구조와 판단

### 3-1. 전체 구조: 전처리형 정적 앱 + 얇은 서버 기능
```
[분기 1회, PC]  공공데이터 + 공식 누리집 → 결합 → 좌표·카카오 매칭 → 네이버·전화·주소·상가정보 검증
                → 앱 데이터(시도별 JSON, 8MB) + 사진 축소본(12,429장, 198MB) + 번호 대장
[배포]          정적 사이트(app/) + 서버 기능 3개(functions/: AI 중계, 공식 소식, 공유 미리보기)
[브라우저]      필터·거리 계산·정렬 전부 로컬, 위치는 기기 안에서만
```
- 앱이 외부 API를 실시간으로 부르지 않는다 → 빠르고, 한도·비용·키 노출 걱정이 적다.
- 분기 갱신은 **이전 분기와 비교해 바뀐 것만** 처리(유지·정보변경·이전·상호변경 의심·신규·제외).

### 3-2. 플랫폼 선택 논리 (무료 조건)
| 역할 | 선택 | 이유 |
|---|---|---|
| 기본 지도·좌표·매칭 | **카카오** | 카드 불필요, 공식 누리집도 카카오 기준 좌표, 한 호출로 좌표+장소 ID+링크, 클러스터 기본 제공 |
| 실재 교차검증·후기 | 네이버 API HUB | 장소 ID는 못 주지만 이름·좌표로 검증 가능(2026-07 이후 신규 발급은 API HUB에서만) |
| 구글 | **링크만** | 결제 계정 필요 → 무료 링크로 평점·후기는 사용자가 직접 확인 |
| 주소 검증 | 도로명주소 API(공공) | 저장 제약 없음, 오타·존재하지 않는 주소 전수 검출 |
| 실재 확인 | 소상공인 상가정보 API | 국세청·카드사 기반, **반경 검색**, 건물관리번호·층·호 |
| 인허가(휴폐업) | 시도했으나 보류 | API 100건/회·일 1만 건, 파일 서버 403 → 대체 채널로 해결 |

### 3-3. "크롤링 대신 링크" 원칙
- 네이버 지도 robots.txt는 모든 봇·AI 봇을 명시적으로 차단 → 자동 수집·AI 브라우저 순회 모두 하지 않음(속도가 아니라 **누가 하느냐**가 기준).
- 114(민간 전화번호부)도 상업 DB라 제외. 캡차 우회는 원칙적으로 하지 않음.
- 대신 **공식 API로 애매한 업소만 골라내고, 사람은 링크를 확인**하는 구조.
- 후기·사진 본문은 저장·복제하지 않고 **채널 바로가기**로 연결 → 법적 부담 없음, 앱도 가벼움.
- 공개 사례로서 "**공식 API와 허용된 방식만으로 만들었다**"가 강점이 된다.

### 3-4. 사진 정책의 진화
1. 공식 사진을 원본 주소로 연결(보관 안 함) → 목록 사진이 평균 1.1MB(최대 5.3MB)라 느리고 공식 서버 시간초과.
2. 화면에 보이는 것만, 동시 6개 제한 → 개선됐지만 여전히 무거움.
3. **목록용 360px 축소본을 미리 생성해 함께 배포**(평균 15KB, 약 70배 가벼움), 상세는 원본 + 축소본 배경. 사용자 결정으로 "링크만" 원칙을 목록용 축소본에 한해 조정.

### 3-5. AI는 "문장 → 필터 조건"만
- 업소 데이터를 AI에 보내지 않는다. AI는 문장을 **JSON 스키마로 강제된 조건**으로 바꾸고, 검색은 앱이 로컬에서 한다 → 토큰 적음, 데이터 유출 없음, 모델 교체 쉬움.
- **규칙 해석 먼저, 못 읽을 때만 AI**(하이브리드) → 대부분 0원·즉시, 무료 한도 보호. 실제로 테스트 중 제미나이 503이 나와 대체 경로의 필요성을 확인.
- 모델 선택: 무료 등급·카드 불필요로 **제미나이**. 클로드는 이중화 후보였으나 비상업 단계라 보류(키만 넣으면 켜지게 설계).
- AI 응답은 **허용 목록으로 재검증**(없는 업종·시설명 무시, 가격 범위 제한).

### 3-6. 규칙 해석기 설계에서 배운 것
- 사전 대조는 **최장 일치**(칼국수 > 국수), **한 글자 키워드 금지**(회 → 회식 오인식).
- 부분 일치 함정: 드라이브 → 세탁(드라이), 아이스크림 → 유아(아이). 부정 전방탐색(`아이(?!스)`)이나 구체어로 한정.
- 정규화 결과가 다시 규칙에 걸리지 않게(짜장면 → 짜장면면).
- 지역: **시도가 나오면 그 시도 안의 시군구만**, 줄임말 사전(충남·전남·경북…), 시도명과 같은 글자로만 잡힌 시군구는 제외(제주 ≠ 제주시), 동명 시군구는 현재 시도 우선.
- 상황어(해장 → 국밥, 회식 → 단체가능, 아이랑 → 유아시설)가 체감 품질을 크게 올린다.
- **회귀 테스트 문장 목록**을 두고 규칙 수정 때마다 돌린다(버그이력 부록).

### 3-7. 번호 대장(영구 ID) 설계
- 같은 업소 판별 키: 공식 업소번호 → 시도+업소명+주소.
- 한 번 준 번호는 영구, 새 업소만 새 번호, 삭제 번호 재사용 금지, 제외는 별도 목록.
- 모의 테스트(1곳 삭제+1곳 추가+순서 섞기)로 13,117곳 번호 유지 확인.

## 4. 디자인

### 4-1. 브랜드·상징
- 자체 엠블럼은 **식별도가 낮다**(사용자 판단) → 공식 "착한가격" 워드마크를 쓰되 **지자체명·정부상징은 제거**(전국 서비스에 특정 지자체 표찰은 사실관계 오류).
- 행정안전부는 **텍스트로만**("행정안전부 착한가격업소 공공데이터 기반"), 정부상징(태극)은 사용 지침 대상이라 미사용.
- "비공식 개인 서비스" 표기는 인트로·더보기에 유지 — 이유는 저작권이 아니라 **오류 책임·문의 창구 혼동 방지**.
- 표찰 실물 사진은 "착한가격업소란?" 설명 화면에서 출처와 함께.

### 4-2. 색
- 공식 스티커 파랑(라이트 #1241BC, 다크 #2F63E0로 밝게 보정) = **신뢰**, 노랑/앰버 = **가격**(이 앱만 보여주는 정보), 초록 = 영업 중.
- 색은 토큰으로 관리, 라이트·다크 동시 설계. 카카오 지도는 다크 테마가 없어 **지도는 밝게, 주변 UI만 다크**.
- 배지를 이미지로 만들면 다크 대응이 어렵다 → 라이트/다크 두 벌 또는 텍스트 배지.

### 4-3. 글꼴·숫자
- Pretendard(무료·한영 조화, 공식 누리집과 같은 계열), 굵기 3단계(400/600/700).
- 가격은 **고정폭 숫자**, 굵게+강조색, 단위(원)는 작고 흐리게.
- 한글은 줄 간격 1.5 정도로 여유, 다크에서는 글자가 가늘어 보이는 점 보정.

### 4-4. 목업 → 결정 → 적용
- 모바일 목업(홈 둘러보기 / 지도 비교), PC 목업 A(격자형 홈)·B(바로 지도)를 **실데이터로** 만들어 보고 결정.
- 로고도 라이트·다크 샘플 페이지로 비교 후 적용(인트로 배경 투명도 12%·20%·33% 중 20%).

## 5. UX

### 5-1. 탐색 순서 ≠ 카드 위계 (사용자 통찰로 교정)
| 구분 | 순서 |
|---|---|
| 탐색(필터) | **위치 → 품목(업종) → 거리 → 가격** |
| 화면 층위 | **지역 → 업종 → 필터 → 검색**(검색은 좁히는 수단이라 목록 바로 위) |
| 카드 표시 | 품목+가격(가장 크게) → 업소명 → 거리·업종·영업 |
| 영업 여부 | 위계가 아니라 **토글 필터** |

### 5-2. 콤보박스 최소화
- 공식 누리집처럼 콤보박스를 늘어놓지 않는다: 평소엔 **지역 2개 + 업종 칩 + 빠른 필터 몇 개**, 나머지는 [필터] 안에.
- 한식(7,700여 곳)만 2차 칩(일반·육류·면류·분식·찌개류·한정식…) — 공식 세부분류 그대로.

### 5-3. 검색 입력의 두 모드
- **단어(띄어쓰기 없음)**: 타이핑하는 대로 즉시 거름.
- **문장(띄어쓰기 있음)**: 자동 조회하지 않고 "Enter를 누르면 문장으로 검색" 안내 → Enter 시 지역·업종·가격 자동 적용, 검색창엔 핵심어만 남김.

### 5-4. 모바일과 PC는 "같은 코드, 다른 배치"
- 모바일: 지도 + 아래 목록 시트(작게·중간·크게, 지도 끌면 자동 작게), 아래 탭 5개(홈·지도·저장·최근·더보기), 상세는 전체 화면+상단 고정 뒤로가기.
- PC: 왼쪽 세로 메뉴, 조작 영역 2줄, 목록·지도·상세 3단, **바로 지도로 시작** + 목록 위 추천 1줄(접이식), 마우스 올림 → 지도 말풍선(PC만), 키보드 ↑↓·Enter·Esc, 휠로 가로 묶음 이동.
- 태블릿(761~1099px)도 따로 확인.

### 5-5. 에어비앤비 참고 — 가져올 것과 아닌 것
- 가져옴: 위쪽 검색 하나 + 아래 탭, **홈의 주제별 가로 추천 묶음**, 업종 아이콘 칩.
- 안 가져옴: 검색 결과의 가로 넘김(둘러보기엔 좋지만 **비교**엔 불리) → 결과는 세로 목록 + 지도.
- 평점·인기 데이터가 없으므로 추천 묶음은 **사실 기반 주제**(5천 원 이하, 지금 영업 중, 이 지역 많은 메뉴, 포장, 주차, 미용·이발). 전체일 땐 음식점 기준.

### 5-6. 위치
- 권한은 **버튼을 누를 때만** 요청, 거부하면 "지도에서 위치 지정"으로 안내, 설정 경로는 더보기에.
- PC는 GPS가 없어 수 km 틀림 → 지도 클릭 지정 우선, GPS 오차 3km 초과 시 확인.
- 기준 위치가 없으면 거리 숨김·"기본순" 표시(0m 표시는 오해).
- GPS 후 **시도·시군구까지 자동 전환**(사용자 실기기 피드백으로 보강).

### 5-7. 설치(홈 화면 추가)·공유
- **설치를 먼저 요구하지 않는다**: 링크로 온 사람에게 가게부터 보여주고, 업소를 본 뒤 **한 번** 제안(7일 유예), 설치했으면 숨김. 첫 화면 가로막는 창은 이탈·검색 불이익.
- 설치 후 사용자 평: "화면 시안성이 더 좋다" → 설치 유도 버튼을 잘 보이게(홈 첫 화면, 더보기 맨 위).
- 브라우저별 안내(크롬·웨일·삼성·엣지·파이어폭스·사파리), 카카오톡 안 브라우저는 "브라우저로 열기".
- 공유: 카카오톡 공식 공유(업소명·가격·사진 카드) + 기본 공유/주소 복사. 링크를 열면 해당 업소 상세가 바로.

### 5-8. 작은 UX 원칙들
- 항상 떠 있는 메뉴보다 **필요할 때만 나타나는 해제 버튼**(기준 위치 ✕).
- 닫기 경로(✕·목록 버튼·휴대폰 뒤로가기)는 **하나의 경로**로.
- 사진 전에는 업종 아이콘을 먼저, 사진이 오면 덮기.
- 정보가 없다고 숨기지 않는다(영업시간 미확인도 목록에 남김).

## 6. 배포

### 6-1. 무료 구성과 선택 이유
- GitHub Pages만으로는 **AI 키를 숨길 곳이 없다** → Cloudflare Pages(정적 + Functions)로 한 곳에서 해결.
- Render 무료(잠들면 첫 접속 30초+)·Oracle 무료 VM(카드 필요)보다 **서버 관리 없음·항상 빠름·카드 없음**.
- 결과: 계정 2개(GitHub·Cloudflare) + 콘솔 설정 몇 곳, **운영비 0원**.

### 6-2. 배포 전 점검이 가장 효과적이었다
- 3회 점검에서 오류 20여 건을 배포 전에 잡음(지역 오인식, 데이터 이상, 성능, 저장소 차단, ID 밀림).
- 점검 순서: 기능 흐름 → 문장 회귀 → **데이터 이상치** → 환경(저장소 차단·다크·태블릿) → 성능 측정 → **운영(분기 업데이트 시 무엇이 깨지나)**.

### 6-3. 배포 후에만 드러난 것
- API 키를 일반 변수로 넣으면 적용 안 됨(비밀로 재등록).
- 공식 누리집이 **클라우드 접속을 차단**(PC에선 되던 수집이 배포 서버에선 실패) → PC 수집본 동봉.
- 카카오톡 공유 링크는 **제품 링크 관리** 등록이 있어야 열림.
- 휴대폰 다크 모드에서만 보이던 로고 가림.
- **교훈:** 로컬 테스트로 안 보이는 것 = 외부 서비스 설정·네트워크 출처·실기기 조합. 배포 직후 체크리스트를 따로 둔다.

## 8. 협업 방식에서 효과적이었던 것 (다음 프로젝트 진행법)

1. **"먼저 프로그램 짜지 말고 검토부터"** — 구성안 문서(개발구성안_검토_v1.md)를 섹션을 늘려가며 확정한 뒤 구현.
2. **"반영하지 말고 검토 의견 먼저"** — 큰 변경(로고·구조 개편·배포 방식)은 의견 → 목업/샘플 → 결정 → 적용.
3. **수치로 판단** — 가격 분포, 메뉴 키워드 커버리지, 매칭률, 요청 횟수, 속도(ms)를 먼저 재고 결정.
4. **사용자의 현장 통찰이 설계를 바꿈** — 간판명≠상호, 영세·고령 업소의 온라인 부재, 탐색 순서, 공식 로고 식별도, 설치 후 시안성.
5. **법·정책 판단은 사용자가, 근거·위험 목록은 Claude가** — C1~C6은 확인할 곳 목록 → 사용자 판단 기록.
6. **실기기 피드백 루프** — 배포 후 휴대폰 확인 6항목 → 즉시 수정 → 재확인(GPS 시군구, 설치, 공유 링크).
7. **기록을 남기며 진행** — 버그이력(원인·재발 방지), 배포설정기록, 운영절차, 배포전검토, 이 문서.
